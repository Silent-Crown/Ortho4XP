## Phase Goal

**As a** developer who scripts Ortho4XP from the command line, **I want to** discover
every build command via `--help`, keep my existing GUI launch and legacy
`lat lon [provider zl]` build invocations working unchanged, and see a real error when
something fails, **so that** I can automate scenery builds unattended without opening the
GUI and without a script silently masking a failed build.

(Derived from the ROADMAP.md Phase 1 Goal — "Users get a discoverable, argparse-based CLI
without any regression to existing invocations or error behavior" — and its four success
criteria; the ROADMAP `**Goal:**` line itself is prose, not yet in user-story format.)

<objective>
Migrate `Ortho4XP.py`'s command-line dispatch from raw positional `sys.argv` parsing to an
argparse-based CLI in a new `src/O4_CLI_Utils.py` module, while preserving every existing
invocation shape byte-for-byte: no-arg GUI launch, and `lat lon [provider zl]` legacy build.
Adds one real subcommand (`build LAT LON [--provider P] [--zl Z]`) with full `--help`
discoverability, fixes coordinate flooring to use `math.floor()` instead of `int()`
truncation, and replaces the bare catch-all failure handler with a real error message +
traceback + non-zero exit code.

Purpose: Turns Ortho4XP into a scriptable tool — CLI-01 through CLI-04 are the full
Phase 1 requirement set, and Phase 2-3 extend this same `O4_CLI_Utils.py` dispatch module
rather than growing the entry point further.

Output: `src/O4_CLI_Utils.py` (new), `Ortho4XP.py` (modified entry point / shim).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Local invoker (interactive user or an unattended script) -> `O4_CLI_Utils` argv/coordinate parsing | `argv` content (lat/lon/provider/zl strings) crosses from an external caller into this process; not a network boundary — the "attacker" model here is a malformed or malicious local script argument, not a remote actor. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|------------|----------|-------------|-------------------|
| T-01-01 | Tampering | `parse_and_floor_coord()` -> `CFG.Tile` -> `FNAMES.build_dir` path construction | medium | mitigate | `parse_and_floor_coord()` range-validates lat in `[-90,89]` and lon in `[-180,179]` and raises before `CFG.Tile` is ever constructed (Task 1); only a floored `int` — never a raw attacker-controlled string — reaches path-building code downstream. |
| T-01-02 | Information Disclosure | `run_and_report()` traceback-to-stderr on crash | low | accept | Intentional per CONTEXT.md: this is a local, single-user CLI tool with no test suite; the traceback goes to the invoking user's own terminal, never to a remote client, so the diagnostic value outweighs the disclosure risk. |
| T-01-03 | Denial of Service | `build_parser()` usage-error path (`required=True` subparsers) | low | accept | argparse's own `sys.exit(2)` on bad/missing subcommand args is the standard, expected CLI failure mode — no resource amplification, no persistence, no state change. |

No package-manager installs occur in this phase (stdlib only: `argparse`, `math`,
`traceback`), so no `T-{phase}-SC` package-legitimacy row applies.
