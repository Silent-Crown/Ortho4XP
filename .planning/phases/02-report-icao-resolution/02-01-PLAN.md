<objective>
**User story:** **As a** scenery scripter, **I want to** ask whether a given ICAO's
tile is already built without opening the GUI, **so that** I can decide what to build
before kicking off a run.

Tracer slice for Phase 2: prove the highest-risk end-to-end path — the ICAO resolver
(BUILD-01, reused by Phase 3) wired all the way to a report — before expanding. This plan
delivers `report coverage --icao <CODE>` for the airport's **containing tile only**
(built/partial/missing), touching every layer the phase will modify: the argparse `report`
subtree, the config var, the hand-rolled MCP-over-HTTP resolver, the D-05 tile predicate,
and the FNAMES path authority. Full 3x3 coverage and the three error-mode messages are the
next plan's expansion; this one proves the wire works.

Purpose: de-risk the one genuinely new block (the ~40-line MCP streamable-HTTP handshake,
MEDIUM-confidence SSE envelope) on the executor's best early-context tokens.
Output: `O4_ICAO_Utils` (resolver), `O4_Report_Utils` (D-05 predicate + cfg reader), the
`report coverage` command, the `mcp_aviation_server_url` config var, and the pytest harness.

**RESEARCH deviations from CONTEXT (implement per RESEARCH, source of truth):**
- D-02 wording says resolve via an `airport://{ident}` resource — that resource does NOT
  exist. Use `tools/call` -> `get_airport_details(ident=...)`; coordinates at
  `airport.coordinates.latitude/longitude`. The D-01/D-02 intent (hand-rolled `requests`
  client, HTTP transport, no new dep) is preserved.
- D-09 names the per-tile config `zOrtho4XP_<latlon>.cfg`; the real filename is
  `Ortho4XP_<latlon>.cfg` (no `z`; the `z` is only on the directory). Handled in Plan 03,
  noted here for the shared cfg reader.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI arg -> resolver | user-supplied ICAO string crosses into an outbound HTTP request |
| aviation server -> resolver | untrusted JSON/SSE response parsed into coordinates |
| Tiles/ filesystem -> report | tile directory names + `.cfg` contents read from disk |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Denial of Service | resolve_icao HTTP calls | medium | mitigate | Explicit `timeout=` (default http_timeout 10.0) on every POST; one attempt, fail fast per D-04. |
| T-02-02 | Tampering | untrusted server payload | medium | mitigate | Validate `airport`/`coordinates` keys exist and lat/lon are finite and in range before returning; `json.loads` only, never eval. |
| T-02-03 | Info disclosure / SSRF | mcp_aviation_server_url | low | accept | URL is operator-set in Ortho4XP.cfg, not per-command input; documented as trusted local/LAN. No per-request override this phase. |
| T-02-04 | Tampering | tile dir names | low | mitigate | Fixture/dir names matched by strict regex; (lat,lon) are ints; all paths built via FNAMES. |
| T-02-05 | Elevation of Privilege | untrusted .cfg content | low | mitigate | read_cfg uses `split("=",1)` plain text — no exec/eval/ast on values. |
| T-02-SC | Tampering | pytest dev install | low | mitigate | pytest is a canonical, widely-used dev-only package (verify at pypi.org/project/pytest); not a runtime dep, no [ASSUMED]/[SUS] packages this phase (RESEARCH Package Legitimacy Audit: no runtime installs). |
</threat_model>
